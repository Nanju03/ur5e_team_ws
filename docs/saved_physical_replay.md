# 실물 저장 경로 빠른 실행

[실물 사용법](real_robot.md) · [계획·이동 최적화](planning_optimization.md) · [v15 높이·하강 변경](side_hover_and_descent.md)

현재 정책은 **v16: 목표 가까운 임시 적재 위치 우선 + 10mm 높은 수평 진입·하강 구간별 속도**입니다.
[임시 위치 선택 기준](near_target_buffer.md)을 확인하세요. 기존 v13/v14/v15 경로는 보존하고 ④에서 새로 계획합니다.
실물 집기·쌓기는 **저장할 때 한 번 충돌 검사하고, 실행 중에는 그 결과를 재사용**합니다.
⑤ 실행에서는 경로를 다시 계산하거나 `/check_state_validity`로 궤적을 재검사하지 않습니다.
현재 장면·로봇 상태 확인과 중지 감시는 계속합니다.

## 사용하는 순서

1. 실제 블록을 처음 배치로 맞추고, 빈 그리퍼와 초기 팔 자세를 확인합니다.
2. GUI에서 장애물·목표·빈칸을 선택하고 **③ 선택 배치를 RViz에 표시**합니다.
3. **④ 저장 경로 불러오기 / 새 경로 계획**을 누릅니다.
   일치하는 저장 경로가 있으면 계산·충돌 검사를 생략하고 불러옵니다.
   없거나 시작 조건이 다르면 새 경로를 계획하고 사전 검사한 뒤 자동 보관합니다.
4. RViz에서 경로를 확인하고 **전체 연속 실행 → ⑤ 실물 집기·쌓기 실행 → OK**로 시작합니다.

단계별 모드에서는 기존처럼 구간마다 OK를 눌러야 합니다. 연속 모드에서는 전체 경로를 한 번 승인합니다.
⑤를 누른 뒤에는 시작 상태·제어기 확인과 경로 미리보기를 준비하는 시간이 남습니다.
팔과 그리퍼의 목표 도달, 손가락 명령 완료, 잡은 뒤 형상 안정 확인도 기다립니다.
이 대기까지 없애거나 구간을 임의로 합쳐서 동작시키지는 않습니다.

GUI를 새로 열어 적용합니다. 드라이버 재연결은 필요하지 않습니다.

```bash
cd ~/ur5e_team_ws
./start_block_real_gui.sh
```

## 이전에 만든 경로

현재 v16은 임시 적재 위치의 우선순위가 달라 기존 v13/v14/v15 파일을 그대로 사용하거나
사전 검사만 다시 수행해서 새 순서로 변환할 수 없습니다. 원본과 라이브러리는 보존합니다.
처음 배치·시작 자세를 맞추고 ④에서 새로 계획하면 v16 자료가 별도 보관됩니다.
Gazebo 성공 ZIP도 실물 경로로 사용하지 않습니다.

GUI의 **저장 경로 사전 검사 (현재 정책)**는 v16 자료를 오프라인 검사해 별도 보관하는 기능입니다.
좌표 편집이나 이전 알고리즘을 새 높이로 바꾸는 기능은 아닙니다.
저장 자료의 부분 수정 조건은 [경로 수정 안내](side_hover_and_descent.md#저장-경로를-조금-수정할-수-있는가)를 참고하세요.

## 저장 위치와 일치 조건

```text
~/.ros/ur5e_a3_stack/physical_path_library/<설정 해시>/<plan_id>/
    recipe.json
    recipe.json.meta.json
    팔·손가락 궤적, 장면, 초기 상태 CDR 파일
```

배치 선택 파일, 모델·보정·플레이트·받침·그리퍼 설정, 속도·검사 정책과 초기 충돌 장면이
일치해야 합니다. 팔 시작 자세는 관절별 0.001rad 이내여야 합니다. 첫 동작이 그리퍼 열기이면
사전에 검사한 열림 범위 안의 현재 손가락 각도를 사용할 수 있습니다.
다른 팔 자세에서 저장 경로로 자동 연결하는 동작은 추가하지 않습니다.

보관 자료에는 1시간 만료를 적용하지 않습니다. ④에서 현재 배치·모델·장면·시작 자세를
대조한 뒤 **실행 검토 세션만 새로 발급**합니다. 이 세션은 기존처럼 1시간 유효하며
⑤와 OK 승인을 거칩니다. 파일을 읽을 때 전체 체크섬을 확인하고 실행할 자료를 메모리에 고정합니다.
GUI를 다시 켜도 라이브러리는 보존됩니다. 팀원과 경로를 공유할 때는 이 폴더도 별도로 복사합니다.

## 구간 사이 시간을 줄인 부분

| 이전 반복 작업 | 현재 동작 |
| --- | --- |
| 각 구간의 전체 보간 경로·파지 형상 충돌 검사 | 저장된 검사 결과와 실측 범위만 대조 |
| 구간마다 모든 CDR 파일 해시·모델·제어기 서비스 재확인 | 파일은 시작 시 확인·고정, 상태는 지속 감시 |
| 각 팔/그리퍼 명령마다 액션 클라이언트 생성·연결 | 작업 동안 클라이언트 재사용 |
| 각 구간마다 감시 요청 전체를 초기화 | 최근 확인 결과·진행 중 요청 재사용 |
| 같은 정지 상태를 확인할 때마다 0.3초 재측정 | 최신 관절 피드백의 정지 이력 재사용 |

부착·해제 시에는 새 장면의 응답을 받아야 합니다. 이전 장면의 늦은 응답으로 새 장면을
승인하지 않습니다. 관절 피드백·그리퍼 센서, 팔 추종 결과, 제어기·하드웨어·모델·장면과
실행 허용 상태의 감시 및 중지·취소 처리는 유지합니다. 이동 중 서비스 응답 제한은 2초,
실제 그리퍼 센서 신선도 제한은 0.5초로 유지합니다.

## 사전 검사 범위

팔 경로는 기존 quintic 표본과 운반 손목 5개 형상을 검사합니다. 이 표본마다 허용 손가락
범위를 최대 0.005rad 간격으로 검사하고 결과를 해당 궤적·장면·모델에 묶습니다.
운반 중 손가락 검사 범위는 0.700~0.733rad입니다. 실측 잡기 기준각에서 0.005rad를 뺀 값도
이 범위 안이어야 하므로, 빠른 재생에서는 잡기 기준각이 0.705rad 이상이어야 합니다.
그 밖의 파지 형상은 이동 전에 중단하며 실행 중 느린 충돌 검사로 자동 전환하지 않습니다.
빈 손의 팔 이동은 명령 완료 오차 ±0.003rad와 이동 중 변화 ±0.003rad를 함께 포함합니다.
손가락 명령은 시작 허용 범위와 목표까지의 전체 열림·닫힘 범위를 검사합니다.

새 계획의 첫 사전 검사는 기존의 단일 손가락 각도 검사보다 표본이 많습니다.
이 비용은 저장 시 한 번 부담하고 같은 조건으로 재실행할 때 생략합니다.
지정한 격자를 표본 검사하는 방식이며 연속 공간 전체나 모든 팔 관절 오차 조합을 검사한 것은 아닙니다.
실제 블록의 배치 확인은 작업자가 수행합니다.

## 로그 확인

```text
STACK_REPLAY_SAVED {...}                         # 재사용 자료 보관 완료
STACK_REPLAY_CACHE_HIT {... "collision_rechecks": 0} # ④ 저장 경로 사용
STACK_REPLAY_CACHE_MISS reason=...               # 일치 자료가 없어 새 계획
STACK_REPLAY_READY {... "collision_rechecks": 0} # ⑤ 경로 재검사 생략
STACK_REPLAY_STEP_TIMING {...}                   # 구간 준비/동작/정지 확인 시간
```

`prepare_seconds`, `action_seconds`, `settle_seconds`로 다음 대기 원인을 구분할 수 있습니다.
실물 전체 작업 시간이나 개선 배율은 현장에서 이 로그로 측정해야 합니다.
중단 후에는 잡힌 블록과 배치를 복구해야 하며, 멈춘 지점부터 자동 재생하는 기능은 아닙니다.

### ④에서 `Another stacking task is running in this ROS domain`

2026-11-05 21:10, 장애물 1번·목표 6번에서 확인한 오류는 저장 경로 조회를 위해
부모 실행기가 먼저 잡은 잠금 때문에 자식 C++ 계획기가 시작하지 못한 코드 오류였습니다.
앞의 `STACK_REPLAY_CACHE_MISS reason=no_prepared_path`는 저장 자료가 없다는 정상 안내입니다.

수정 후에는 저장 경로 조회는 부모가 잠근 상태에서 수행하고, 새 계획이 필요하면 잠금을
해제해 C++ 계획기가 직접 잡도록 합니다. 계산 종료 후 부모가 다시 잠금을 잡은 뒤 검증합니다.
실제로 다른 작업이 잠금을 보유한 경우에는 계속 차단합니다. 잠금 파일을 삭제할 필요는 없습니다.
이 수정은 ④가 새로 시작하는 작업 노드에 적용되므로 현재 GUI에서 ④를 다시 진행할 수 있습니다.
드라이버 재연결이나 저장 경로의 재변환은 필요하지 않습니다.

### 이전 ④ 작업이 남아 ③도 잠금 오류가 나는 경우

2026-11-05 21:23에는 앞선 수정 전에 시작한 21:13의 `physical_plan` 작업이 남아 있었습니다.
중지 요청은 받았지만 오류를 낸 자식 계획 프로그램의 종료를 계속 기다려 부모가 잠금을
보유하고 있었고, 이후 ③도 같은 잠금에 막혔습니다. 이 실패한 이전 작업을 확인해 종료하고
domain 0의 작업 잠금 두 개가 해제된 것을 확인했습니다. 드라이버와 로봇 목표는 건드리지 않았습니다.

현재 코드는 계획 프로그램의 치명적 오류나 중지 요청 뒤 SIGINT → SIGTERM → SIGKILL 순서로
자신이 만든 계획 프로세스 그룹만 제한 시간 안에 정리합니다. 중복 작업은 ROS 실행 스레드를
만들기 전에 거절하여 오류를 낸 ③ 프로세스가 종료를 기다리며 남는 경우도 방지했습니다.
잠금 파일을 삭제해 우회하는 방식은 사용하지 않습니다.
수정 후 같은 GUI에서 ③을 다시 진행할 수 있습니다. 실제 다른 계획·실행이 진행 중일 때는
계속 차단되며, 해당 작업이 완료되거나 중지 처리를 끝낸 뒤 표시합니다.
