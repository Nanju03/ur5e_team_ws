# 실물 실행의 대기 시간과 속도·가속도 조절

> 아래 수치와 0.20 배율은 2026-11-04의 과거 분석이다.
> 2026-11-05 적용한 로컬 계획 검증·직접 이동·1.00 이동 배율은 [최신 안내](planning_optimization.md)를 따른다.

[실물 사용법](real_robot.md) · [README](../README.md)

2026-11-04 점검 당시 코드와 저장된 장애물 11번·목표 14번의 실물 경로를 기준으로 확인했다.
이 점검에서는 속도·가속도 값을 변경하거나 실제 로봇에 이동 명령을 보내지 않았다.

아래 시간 분석은 **19층까지 수직·20층부터 측면·상단 120mm 접근으로 바꾸기 전** 경로의 기록이다.
새 접근 방식의 시간은 ④에서 다시 생성한 계획으로 확인한다. 현재 접근 방식은 [실물 사용법](real_robot.md)에 정리했다.

## ④ 계획과 ⑤ 실행에서 하는 일

**④는 전체 경로를 생성하고 검증해 저장한다.** IK·충돌 경로, 동작 시간, 손가락 개폐,
부착·해제와 임시 적재 순서를 계획하고 제어기의 보간·추종 오차를 포함한 상태를 검사한다.

**⑤는 저장된 경로를 불러와 현재 상태와 맞는지 확인한다.** 전체 경로를 새로 계획하지는 않는다.
계획 파일·보정·배치의 변경 여부, 현재 관절·정지 상태, 제어기와 장면을 확인하고
실제로 멈춘 그리퍼 형상을 반영해 다음 구간을 검증한 뒤 명령한다.
전체 미리보기의 작성·승인 준비와 이 검사에도 시간이 걸린다.

연속 모드에서 승인 대기 없이 동일 구간을 연달아 검사하던 부분은 **한 번으로 줄였다**.
단계별 모드는 승인 전·후 두 번 검사하며, 두 모드 모두 **실제 동작 직전 검증과 상태 검사**는 유지한다.
관련 승인·집기·취소·복구 검사 420개가 통과했다.
[검사 로그](../log/stack_speed_execution_tests_20261104.log)

전체 경로의 파일 1,187개·약 45MB를 해시 확인하는 데 이번 PC에서 약 0.117초가 걸렸다.
이는 파일 검사 한 번의 측정이며 전체 시작 지연이나 현재 상태 충돌 검사 시간을 뜻하지 않는다.
[실측·단계별 시간](../log/stack_speed_analysis_20261104.json)

## 현재 적용되는 속도·가속도

| 구간 | 속도 설정 | 현재값 | 가속도 설정 | 현재값 |
| --- | --- | --- | --- | --- |
| 집기·놓기의 최종 진입 | `approach_velocity_scaling` | 0.05 | `approach_acceleration_scaling` | 0.05 |
| 들어 올림·운반·후퇴·대기 자세 이동 | `transfer_velocity_scaling` | 0.20 | `transfer_acceleration_scaling` | 0.20 |

이 수치는 **m/s가 아니라 관절별 모델 한도에 곱하는 배율**이다. 0.20은 해당 한도의 20%라는 뜻이다.
기본 관절 한도는 URDF·`joint_limits.yaml`에 있고, 배율은 그 한도 아래에서 경로의 시간화를 조절한다.
([MoveIt 공식 속도 설정 설명](https://moveit.picknik.ai/humble/doc/examples/time_parameterization/time_parameterization_tutorial.html))

현재 실물 검증기는 별도 가속도 한도가 없는 관절에 **1rad/s²**를 기준으로 사용하므로
현재 최종 가속도 한도는 접근 0.05rad/s², 운반 0.20rad/s²다. 짧은 구간을 매번 정지하며 움직여
가속도 제한의 영향이 크다.

GUI의 **팔 시운전 속도 (최대 0.05)**는 블록 없는 팔 시운전용이다.
④ 실물 집기·쌓기의 위 배율은 현재 이 입력창으로 바뀌지 않는다.

## 어디를 변경해야 하나

현재는 실물 배율이 여러 위치에 고정돼 있어 설정 한 곳만 바꾸는 구조가 아니다.

| 파일 | 역할 |
| --- | --- |
| [stack_blocks.yaml](../src/ur5e/ur5e_a3_grid/config/stack_blocks.yaml) | 공통 기본값. 실물 런치에서 아래 값으로 덮어쓴다. |
| [block_task.launch.py](../src/ur5e/ur5e_block_bringup/launch/block_task.launch.py)의 `if physical:` | 실물에 최종 적용하는 네 배율을 지정한다. |
| [physical_stack.py](../src/ur5e/ur5e_block_bringup/ur5e_block_bringup/physical_stack.py)의 `ARM_SPEEDS`·`validate_recipe()` | 해당 배율의 경로만 허용한다. 런치와 다르면 실행을 거절한다. |
| [stack_gui.py](../src/ur5e/ur5e_a3_grid/scripts/stack_gui.py)의 `save_selection()`·안내 문구 | 배치 파일에 저장하는 값과 사용자 표시를 맞춘다. |

실제로 조절하려면 다음 순서로 적용한다.

1. `block_task.launch.py`에서 접근·운반의 속도와 가속도 네 배율을 정한다.
2. `physical_stack.py`의 `ARM_SPEEDS`와 `validate_recipe()`의 가속도 허용값을 같은 프로파일로 맞춘다.
   현재는 속도와 가속도에 같은 배율을 요구한다. 둘을 독립적으로 지정하려면 이 검증 정책도 분리해야 한다.
3. 공통 기본값·GUI 저장값·안내와 회귀 검사의 기대값을 같은 프로파일로 맞춘다.
   검증 정책을 바꿀 때는 `RECIPE_POLICY`도 갱신해 이전 검토 경로와 구분한다.
4. 빌드·설치 후 **④에서 변경한 속도·가속도로 새로 계획**하고 시간과 경로를 확인한다.
   단계별 실물 시험을 거쳐 연속 실행을 사용한다.

배율을 크게 하면 지정한 한도를 높이고, 작게 하면 낮춘다. 예를 들어 0.20→0.40은 한도를 2배로
정하는 것이며 완료 시간이 절반이 된다는 뜻은 아니다. 가속도·감속·구간별 정지와 경로 형상도 시간을 결정한다.
현재 코드에서 YAML만 수정하면 실물 런치의 고정값이 우선하고, 런치만 바꾸면 실행기의 검증 정책과 불일치한다.

## 5분 목표와 현재 계획 시간

현재 저장된 경로는 최종 블록 22개·임시 운반 1회, 총 운반 23회다.
**계획된 동작 시간 합계만 약 32분 39초**이며 실행 전/구간별 검사와 실제 그리퍼 응답 대기는 별도다.

| 구간 | 저장된 동작 시간 |
| --- | --- |
| 운반·자세 변경 | 약 18분 46초 |
| 집기·놓기 접근 | 약 8분 37초 |
| 상승 | 약 3분 1초 |
| 후퇴 | 약 1분 8초 |
| 손가락 동작 | 약 1분 7초 |

같은 경로·정지점과 각 구간의 시간 분포를 유지하고, 관절별 속도·가속도 한도에 맞춰
시간만 균등 축소하는 낙관적인 계산도 수행했다. **새 경로 계획이나 실물 시험 결과가 아니다.**

| 계산 조건 | 동작 시간 추정 |
| --- | --- |
| 현재 배율 | 약 32분 39초 |
| 속도만 2배, 가속도 유지 | 약 32분 39초 |
| 속도·가속도 모두 2배 | 약 23분 25초 |
| 두 배율을 모두 1.0으로 가정한 모델상 계산 | 약 13분 18초 |

마지막 행은 실물 사용을 권장하는 설정이 아니다. 이 계산은 현재 시간 분포를 축소하는 방식의 추정이며
최적 제어의 절대 최소 시간이나 1.0 배율의 실물 파지·적재 가능성을 증명하지 않는다.
[계산 조건·결과](../log/stack_retiming_estimate_20261104.json)

5분 안에 23회 운반하려면 검사·그리퍼·이동을 모두 포함해 회당 평균 약 13초여야 한다.
현재는 속도 배율만 높이기보다 **큰 우회 경로·반복 대기 자세·이동 높이·중간 정지와 검증 비용**을
함께 줄이는 설계가 필요하다는 판단이다. 시간 제한에 계획 시간이 포함되는지와 관계없이,
현재 동작 경로 자체를 단축하는 작업이 필요하다.

## 펜던트 속도 슬라이더

UR의 `scaled_joint_trajectory_controller`는 로봇이 보고하는 실행 배율에 맞춰 경로 진행을 늦춘다.
펜던트 속도 슬라이더와 로봇 측 제한이 추가 감속에 영향을 준다.
([UR 제어기 설명](https://docs.universal-robots.com/Universal_Robots_ROS2_Documentation/doc/ur_robot_driver/ur_controllers/doc/index.html))

이번 읽기 점검에서는 `/speed_scaling_state_broadcaster/speed_scaling`이 **100.0**이었다.
이 PC의 Humble broadcaster는 0~1 내부 배율에 100을 곱해 발행하므로 **100%**를 뜻한다.
([Humble 구현](https://raw.githubusercontent.com/UniversalRobots/Universal_Robots_ROS2_Driver/humble/ur_controllers/src/speed_scaling_state_broadcaster.cpp))
따라서 측정 당시 슬라이더의 추가 감속이 느림의 주원인은 아니었다.

다음은 값을 읽기만 하는 명령이다.

```bash
source ~/ur5e_team_ws/env.bash
export ROS_DOMAIN_ID=0
ros2 topic echo /speed_scaling_state_broadcaster/speed_scaling --once
```
